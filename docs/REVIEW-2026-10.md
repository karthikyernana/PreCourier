## Design issues not changed

- SQLite uses one process-wide application lock and one connection. This is appropriate for the current single-node MVP, but it is a throughput ceiling; moving to pooled PostgreSQL is a planned deployment change rather than a Stage 0 bug fix.
- Provider calls and reconciliation remain partial. The outbox records intent, but no production provider is enabled, so webhook replay and provider acceptance semantics cannot be fully validated yet.
- The audit export intentionally retains operational address data inside the audit chain while redaction is applied at export boundaries. A complete retention/deletion policy needs product and compliance decisions, not an isolated code change.
- Incentive and discount accounting is still incomplete for live prepaid conversion because those actions are disabled in the MVP decision path. Extending it requires the payment lifecycle and verified callbacks.
- The API's fail-open error contract says `release: true` for all errors, including malformed requests. That is the documented integration contract for this MVP, but production integrations should separately distinguish “no reliable order identity” from a known order.
- The webhook module provides HMAC primitives only; replay-window enforcement and endpoint integration remain future work.

## Stage 1 — profit-decision engine

Stage 1 adds a pure `RiskModel` seam with the deterministic `RuleRiskModel`, cause-level
PPM probabilities, documented external-signal blending, integer-paise action economics,
brute-force action selection, deterministic merchant holdout assignment, provider
interfaces, fake providers, Razorpay test-mode request construction, and replay-window
webhook verification. Existing behavior remains fail-open and the existing Stage 0
suite remains green (214 passed, 2 skipped).

Keep/replace decisions: `ledger.py` remains the source of truth for rupee outcomes,
costs, and derived thresholds; the Stage 1 engine only ranks actions and consumes
merchant economics. `intelligence.py` remains the source of observable features and
diagnosis; cause probabilities are layered on those features by `RuleRiskModel`.
`states.py` remains the lifecycle and fail-open boundary, while `guards.py` remains
the policy enforcement point. The old one-cause `RuleDecider` is retained for
backward-compatible deployments and tests; `ProfitDecisionDecider` is the Stage 1
adapter for live wiring. The new fixed action catalogue is retained only as a pure
primitive fallback; configured decisions use `specs_from_config` so merchant costs
are not duplicated.

`./.venv/bin/python -m precourier.backtest --seed 42 --sensitivity --ten-seeds`.
On the seed-42 500-order run, net contribution was agent Rs 106,551.80,

Known limits: payment and messaging provider execution and webhook routing are
still adapter seams in this checkout; Razorpay production credentials and WhatsApp
Cloud API are intentionally not enabled. Rule probabilities are priors, not trained
calibration. The live order path now persists the richer rupee action explanation
beside the immutable decision row.
